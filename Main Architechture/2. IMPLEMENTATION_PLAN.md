## 1. Philosophy

This project is for **one person, for life**. That changes everything:

- **Simplicity beats scalability.** We are not building for 1,000 users. We are building for one.
- **Zero-dependency architecture.** Every new service (Redis, Celery, PostgreSQL) is a new thing that can break. We avoid them.
- **SQLite is our database.** It requires no server, no config, no RAM when idle, and can store decades of daily digests.
- **One process, one container.** The web server, the scheduler, the scraper, and the summarizer all live in the same Python process. This keeps RAM under 600 MB — comfortable on a 1 GB VPS.
- **Code you can read in a year.** No microservices, no message brokers, no distributed tracing. Just well-organized Python modules.
- **Multi-modal ingestion.** RSS articles + YouTube transcripts + Podcast transcripts — all unified through the same LLM summarization pipeline.
- **Prompts as data.** All LLM prompts live in Markdown files, not Python code. Edit them without redeploying.

**What we keep from your original proposal:**
- ✅ Docker for environment parity (scraping works identically everywhere)
- ✅ Playwright for JS-heavy sites
- ✅ Map-Reduce chunking for token limits
- ✅ Exponential backoff for LLM retries
- ✅ Web interface for cross-device access and historical browsing

**What we drop:**
- ❌ Redis (no message broker needed — the scheduler calls the scraper directly)
- ❌ Celery (no worker queues — `asyncio` or threads handle parallelism)
- ❌ PostgreSQL (SQLite handles single-user workloads beautifully)
- ❌ React/Next.js (server-rendered Jinja2 templates give us a UI in 1/10th the code)

### Data Flow

```
SCHEDULED RUN (daily, triggered by APScheduler):

  1. Scheduler fires media scrape job
  2. RSS phase: reads DB sources (seeded from OPML) → fetches RSS feeds →
     extracts article text via trafilatura/Playwright
  3. YouTube phase: scans active YouTube channels → fetches recent video
     transcripts via youtube-transcript-api
  4. All raw content (articles + transcripts) stored in SQLite (status = 'raw')
  5. Summarizer picks up raw content (articles and transcripts)
  6. Summarizer chunks each item, calls LLM in parallel (map),
     then synthesizes sub-summaries (reduce)
  7. Daily digest is generated and stored (unified across media types)
  8. YouTube OAuth subscription sync runs weekly (if configured)

WEB REQUEST (anytime):

  Browser → FastAPI route → SQLite query → Jinja2 template → HTML response
  (The web layer NEVER touches the scraper or LLM directly — it only reads SQLite)
```

## 5. Database Schema (SQLite)

```sql
-- Stores RSS feed sources (populated from OPML file)
CREATE TABLE sources (
    id              INTEGER PRIMARY KEY AUTOINCREMENT,
    name            TEXT    NOT NULL,
    feed_url        TEXT    NOT NULL UNIQUE,
    site_url        TEXT,                           -- optional homepage
    category        TEXT,                           -- e.g. "politics", "markets"
    is_active       INTEGER DEFAULT 1,             -- soft-delete feeds
    last_fetched_at TIMESTAMP,
    created_at      TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

-- Each individual article scraped from an RSS feed
CREATE TABLE articles (
    id              INTEGER PRIMARY KEY AUTOINCREMENT,
    source_id       INTEGER REFERENCES sources(id),
    url             TEXT    NOT NULL UNIQUE,        -- deduplication key
    title           TEXT    NOT NULL,
    snippet         TEXT,                           -- original RSS description
    raw_text        TEXT,                           -- full extracted article text
    summary_text    TEXT,                           -- LLM-generated summary
    author          TEXT,
    published_at    TIMESTAMP,
    fetched_at      TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    status          TEXT    DEFAULT 'raw',          -- 'raw' | 'summarizing' | 'summarized' | 'failed'
    chunk_count     INTEGER,                       -- how many chunks the article was split into
    error_message   TEXT                            -- if status = 'failed'
);

-- One daily digest per calendar date (IST)
CREATE TABLE daily_digests (
    id              INTEGER PRIMARY KEY AUTOINCREMENT,
    date            DATE    NOT NULL UNIQUE,        -- calendar date (IST)
    title           TEXT,                           -- "Daily Digest — 29 May 2026"
    summary_text    TEXT,                           -- synthesized digest of the day
    article_count   INTEGER,                       -- how many articles summarized
    source_count    INTEGER,                       -- how many sources covered
    status          TEXT    DEFAULT 'generated',   -- 'generated' | 'regenerating'
    created_at      TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_at      TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

-- Which articles belong to which daily digest
CREATE TABLE digest_articles (
    digest_id       INTEGER REFERENCES daily_digests(id),
    article_id      INTEGER REFERENCES articles(id),
    inclusion_order INTEGER,                       -- position in digest
    PRIMARY KEY (digest_id, article_id)
);

-- Scraping run audit log (optional, for debugging)
-- YouTube channels (manually added or OAuth-synced)
CREATE TABLE IF NOT EXISTS youtube_channels (
    id              INTEGER PRIMARY KEY AUTOINCREMENT,
    channel_id      TEXT    NOT NULL UNIQUE,
    channel_name    TEXT    NOT NULL,
    channel_url     TEXT,
    thumbnail_url   TEXT,
    source_type     TEXT    DEFAULT 'youtube',  -- 'youtube' | 'podcast'
    is_active       INTEGER DEFAULT 1,
    detail_level    TEXT    DEFAULT 'detailed',  -- 'high-level' | 'detailed'
    last_fetched_at TIMESTAMP,
    created_at      TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

-- Individual YouTube videos with transcripts
CREATE TABLE IF NOT EXISTS youtube_videos (
    id              INTEGER PRIMARY KEY AUTOINCREMENT,
    channel_id      INTEGER REFERENCES youtube_channels(id),
    video_id        TEXT    NOT NULL UNIQUE,
    title           TEXT    NOT NULL,
    url             TEXT    NOT NULL,
    description     TEXT,
    transcript_text TEXT,
    summary_text    TEXT,
    published_at    TIMESTAMP,
    fetched_at      TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    status          TEXT    DEFAULT 'raw',       -- 'raw' | 'summarizing' | 'summarized' | 'failed'
    chunk_count     INTEGER DEFAULT 0,
    llm_provider    TEXT,
    error_message   TEXT
);

CREATE TABLE scrape_log (
    id              INTEGER PRIMARY KEY AUTOINCREMENT,
    started_at      TIMESTAMP,
    finished_at     TIMESTAMP,
    feeds_total     INTEGER,
    feeds_success   INTEGER,
    feeds_failed    INTEGER,
    articles_new    INTEGER,
    articles_skipped INTEGER,
    error_details   TEXT,                           -- JSON blob of per-feed errors
    created_at      TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
```

**Design notes:**
- `articles.url` is UNIQUE — this is how we deduplicate. If the same article appears in two scrapes, we skip it.
- `articles.status` lets us track which articles need summarization. The summarizer queries `WHERE status = 'raw'`.
- `daily_digests.date` is a calendar date (no time). One row per day.
- `scrape_log` is an audit trail. Helps debug "why didn't the scraper run on Tuesday?"

**Connection pattern:**

```python
# app/database.py
import sqlite3
from pathlib import Path
from app.config import settings

DB_PATH = Path(settings.data_dir) / "aggregator.db"

def get_db() -> sqlite3.Connection:
    """Return a connection. Caller is responsible for closing it."""
    conn = sqlite3.connect(str(DB_PATH))
    conn.row_factory = sqlite3.Row  # Access columns by name
    conn.execute("PRAGMA journal_mode=WAL")  # Better concurrent reads
    conn.execute("PRAGMA foreign_keys=ON")
```

**Text Chunking:**

```python
# app/summarizer/chunker.py
from langchain_text_splitters import RecursiveCharacterTextSplitter

def create_splitter(chunk_size=4000, overlap=400):
    return RecursiveCharacterTextSplitter(
        chunk_size=chunk_size,
        chunk_overlap=overlap,
        separators=["\n\n", "\n", ". ", " ", ""],  # paragraphs → sentences → words
        length_function=len,
    )

def chunk_article(text: str, chunk_size=4000, overlap=400) -> list[str]:
    """Split article into overlapping chunks at natural boundaries."""
    return create_splitter(chunk_size, overlap).split_text(text)
```

**Why overlap matters:** If chunk 1 ends mid-sentence and chunk 2 starts fresh, the LLM loses context at the boundary. 10% overlap means the LLM sees the transition, producing better sub-summaries.

**LLM Client with Retry:**

```python
# app/summarizer/llm.py
MAX_RETRIES = 5
BASE_DELAY = 2  # seconds → exponential: 2, 4, 8, 16, 32

def call_llm(prompt: str, provider=None) -> str:
    """Call LLM with exponential backoff on 429/500 errors."""
    provider = provider or settings.llm_provider
    for attempt in range(MAX_RETRIES):
        try:
            if provider == "gemini":
                return call_gemini(prompt)
            elif provider == "groq":
                return call_groq(prompt)
        except Exception as e:
            if "429" in str(e) or "500" in str(e):
                time.sleep(BASE_DELAY * (2 ** attempt))
                continue
            raise  # Non-retryable error
    raise Exception(f"LLM call failed after {MAX_RETRIES} retries")
```

**Map-Reduce Orchestration:**

```python
# app/summarizer/service.py
from concurrent.futures import ThreadPoolExecutor, as_completed

def summarize_article(raw_text: str) -> str:
    """Full map-reduce pipeline for one article."""
    if len(raw_text) < settings.chunk_size:
        return call_llm(f"Summarize concisely:\n\n{raw_text}")

    # MAP: Parallel chunk summarization
    chunks = chunk_article(raw_text)
    sub_summaries = []
    with ThreadPoolExecutor(max_workers=5) as executor:
        futures = {executor.submit(call_llm, f"Summarize:\n\n{c}"): i for i, c in enumerate(chunks)}
        for future in as_completed(futures):
            sub_summaries.append(future.result())

    # REDUCE: Synthesize into one summary
    combined = "\n\n---\n\n".join(sub_summaries)
    return call_llm(
        "Synthesize these sub-summaries into one cohesive summary. "
        "Remove redundancies. Preserve all key facts.\n\n" + combined
    )

def generate_daily_digest(date_str: str) -> str:
    """Topic-wise daily digest from all summarized articles."""
    conn = get_db()
    articles = get_articles_for_date(conn, date_str)
    summaries = "\n\n---\n\n".join(
        f"[{a.source_name}] {a.title}\n{a.summary_text}" for a in articles
    )
    return call_llm(
        "You are a news editor. Synthesize these summaries into a daily digest. "
        "Group related stories. Use section headings. Neutral tone. "
        "2-4 paragraphs per section.\n\n" + summaries
    )
```

### Phase 5: Scheduler & Integration (1 hour)

**Goal:** Wire APScheduler to call scraper → summarizer → digest daily. One process.

```python
# app/main.py
from contextlib import asynccontextmanager
from apscheduler.schedulers.background import BackgroundScheduler
from app.scraper.service import run_scrape
from app.summarizer.service import run_summarization, generate_daily_digest

scheduler = BackgroundScheduler()

@scheduler.scheduled_job('cron', hour=20, minute=0, timezone='Asia/Kolkata')
def daily_scrape_and_summarize():
    """Run every day at 8:00 PM IST."""
    logger.info("Starting daily scrape...")
    run_scrape()
    logger.info("Scrape complete. Starting summarization...")
    run_summarization()
    generate_daily_digest(today_ist_str())
    logger.info("Daily digest ready.")

@asynccontextmanager
async def lifespan(app: FastAPI):
    init_db()
    scheduler.start()
    logger.info("Scheduler started. Daily scrape at 20:00 IST.")
    yield
    scheduler.shutdown()

app = FastAPI(lifespan=lifespan)
app.include_router(web_router)
```

**Why this works:** APScheduler sleeps 99.99% of the time. During daily scrape (~2-5 min), the web server still responds to requests. RAM spikes temporarily (Playwright) but returns to baseline.

## 11. Summary: Why This Works

| Constraint | Solution |
|------------|----------|
| **Free for life** | LLM free tiers. $5/mo VPS. SQLite $0. No other costs. |
| **Scraping parity** | Docker = identical Playwright env everywhere. YouTube transcripts use no browser. |
| **Token limits** | Map-Reduce chunking at paragraph boundaries with overlap. Parallel LLM calls. |
| **LLM reliability** | Exponential backoff (up to 5 retries). Gemini → Groq fallback. |
| **Cross-device access** | Web UI. Tailscale VPN for secure access. |
| **Historical browsing** | SQLite stores every article, transcript, and digest. Browse by date, source, creator, keyword. |
| **Beginner-friendly** | No microservices. Raw SQLite. Dataclasses. One process. ~20 files, ~1,200 lines. |
| **Maintainable for life** | Modular but not distributed. One log file. One command to deploy. |
