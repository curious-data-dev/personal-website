# Project Overview:

A personalized news aggregation and summarization engine designed to combat "information overload" by transforming high-volume, low-substance news articles into concise, daily digestible summaries.

# Current Implementation:

* **Data Acquisition:** Python script utilizing RSS feeds and web scraping.
* **Processing:** Summarization via third-party Cloud LLM APIs.
* **Delivery:** Daily digests sent via Google SMTP (Email).
* **Deployment:** GitHub Actions.

## Current Technical Constraints & Failures:

1. **Environment Parity Issues:** Scraping logic succeeds in local environments but fails in Ubuntu-based GitHub Actions runners (likely due to headless browser configurations or IP blocking).
2. **Token Limit Constraints:** Large volumes of scraped text exceed the context window/token limits of the current LLM provider.
3. **Reliability/SLA Issues:** The pipeline has a single point of failure; dependency on third-party LLM uptime makes the system fragile.
4. **Lack of Data Persistence:** No historical storage. Users cannot perform temporal analysis or review past summaries (e.g., comparing news from 30 days ago to today).

# Future Roadmap:

* **Phase 1 (Current Goal):** Transition from an email-based notification system to a centralized, cross-device web application. The app must support historical data retrieval.
* **Phase 2 (Long-term):** Expand into a personal life-management dashboard (wealth tracking, expense management, goal tracking).

# The Proposed "New" System Architecture

To transition to a web app, I suggest a Three-Layer Architecture:

The core philosophy here is Decoupling. We want to separate the discovery of news from the processing of news and the serving of news.

## A. The Ingestion Layer (The Producer)

- Role: High-frequency polling of RSS feeds and initial web scraping.
- Tech Stack: Python, Playwright (to handle SPAs and JS-heavy sites), APScheduler.
- Logic:
  - Instead of scraping and then immediately calling an LLM, the Ingestion Layer's only job is to find content.
  - It scrapes the article, extracts the raw text, and writes it to the Database with a status of STATUS_RAW.
  - Once the write is successful, it pushes a Job_ID into the Message Broker.
- Why this solves Scraping Issues: By using Playwright inside a Docker container, we ensure the browser environment (dependencies,
  fonts, headless config) is identical in dev and production.

## B. The Orchestration Layer (The Broker & Worker)

- Role: Managing the heavy, unreliable, and expensive LLM calls.
- Tech Stack: Redis (Message Broker), Celery (Task Queue), Python Workers.
- Logic (The "Map-Reduce" Pattern):
  1. Worker Pickup: A worker pulls a Job_ID from Redis.
  2. Contextual Chunking: The worker fetches the raw text from the DB. It uses a Recursive Character Text Splitter (splitting on
     paragraphs $\rightarrow$ sentences $\rightarrow$ words) to create chunks with an overlap (e.g., 10-15% overlap) to maintain
     semantic continuity between chunks.
  3. Map Phase: The worker sends multiple parallel requests to the LLM API (one per chunk).
  4. Reduce Phase: The worker takes the $N$ resulting summaries and sends them back to the LLM with a prompt like: "Synthesize these
     sub-summaries into one cohesive daily digest."
  5. State Update: The worker updates the DB record to STATUS_COMPLETED and stores the final summary.
- Why this solves Token/Reliability Issues:
  - Token Limits: Chunking prevents "Context Window Overflow."
  - Reliability: If the LLM API returns a 429 Too Many Requests or a 500 Internal Server Error, Celery uses Exponential Backoff to
    retry the task later without losing the original scraped data.

## C. The Persistence Layer (The Source of Truth)

- Role: Long-term storage for temporal analysis and history.
- Tech Stack: PostgreSQL.
- Relational Schema Design:
  - sources: id, name, rss_url, category, frequency
  - articles: id, source_id, url, title, raw_text, summary_text, status (enum), created_at
  - users: id, email, preferences (JSONB)
- Why this solves Data Persistence: You no longer rely on transient memory or email logs; every piece of data is queryable by date,
  source, or keyword.

## D. The API & Presentation Layer (The Interface)

- Role: Serving the stored data to the user.
- Tech Stack: FastAPI (Backend), React/Next.js or Streamlit (Frontend).
- Logic: The Frontend never talks to the Scraper or the LLM. It only talks to the FastAPI layer, which performs optimized SQL queries
  against the PostgreSQL DB.

## 2. Technical Deep Dive: Addressing your Constraints

### The "Environment Parity" Problem (Dockerization Strategy)

To solve the "works on my machine, fails on GitHub Actions" issue, we will use Docker Compose. We will define a docker-compose.yml thatspins up:

1. app-scraper: A container with Python + Playwright + Chromium installed.
2. app-worker: A container for Celery.
3. app-api: A container for FastAPI.
4. db: A PostgreSQL container.
5. redis: A Redis container.

This creates a reproducible ecosystem. The exact same Linux environment used by the developer is what the GitHub Action runner will pull
and execute.

### The "Token Limit" Problem (Semantic Chunking)

A common mistake is splitting text by character count. This cuts words in half and ruins LLM performance.

- Better approach: Use a library like LangChain's text splitters. It looks for the nearest newline or period to ensure chunks are
  semantically coherent.
- Overlap: By including the last 200 tokens of "Chunk 1" at the start of "Chunk 2," the LLM understands the transition, preventing
  information loss at the boundaries

1. The Worker Layer (The "Engine"):
   - Runs inside Docker.
   - Uses a Scraper to find news.
   - Uses a Task Queue to manage work.
   - Uses Chunking to talk to the LLM.
2. The Storage Layer (The "Memory"):
   - A Database that stores everything the Engine finds.
3. The Presentation Layer (The "Face"):
   - A Web Backend (using FastAPI) that talks to the Database.
   - A Web Frontend (a simple website) where you log in to read your historical summaries
