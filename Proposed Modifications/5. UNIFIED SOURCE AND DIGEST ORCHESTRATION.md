# Unified Source and Digest Orchestration

**Date:** 2026-06-27  
**Status:** Problem definition and agreed product behavior — not implemented  
**Related requirement:** `1. PRODUCT MANAGER VIEW.md`, section 2.2  
**Related plan:** `4. ASYNC YOUTUBE TRANSCRIPT PIPELINE.md`

---

## 1. Purpose

The application currently presents RSS and YouTube as two separate features. Both features perform the same fundamental job:

1. collect information from configured sources;
2. extract usable text;
3. summarize individual items with an LLM;
4. synthesize those summaries into a dated daily digest;
5. present the digest and its underlying sources to the user.

The outputs should remain separate because RSS articles and YouTube videos are different consumption experiences. However, source management and pipeline execution should not behave like unrelated systems.

This document defines the agreed product model for a unified control plane with separate RSS and YouTube digest sections.

---

## 2. Problem Statement

The RSS and YouTube pipelines have overlapping responsibilities but inconsistent management and user experience.

Examples of the inconsistency include:

- RSS digests support previous and next date navigation; YouTube digests do not.
- RSS has a dedicated historical browsing experience; YouTube history is not exposed equivalently.
- RSS sources and YouTube channels are managed in different places and with different controls.
- Manual operation is fragmented across separate RSS scraping, YouTube scraping, and summarization actions.
- A user cannot select a temporary combination of RSS feeds and YouTube channels and run one complete workflow.
- Job status is presented by technical operation rather than as one coherent content-processing run.

The result is a system that has two similar pipelines but no consistent operational model.

---

## 3. Product Principle

> **One control plane, multiple ingestion adapters, separate digest outputs.**

The system should centralize source selection, run orchestration, status, and common date behavior. It should preserve separate RSS and YouTube destinations.

```text
Unified Sources
      |
      +-- RSS feeds
      +-- YouTube channels
      |
      v
One collective fetch-and-summarize run
      |
      +-- RSS ingestion ------> RSS item summaries ------> RSS daily digest
      |
      +-- YouTube ingestion --> Video summaries --------> YouTube daily digest
```

The intention is not to combine RSS and YouTube into one mixed digest.

---

## 4. Agreed Decisions

### 4.1 Centralized source management

There will be one source-management experience containing both:

- RSS feeds;
- YouTube channels.

Every source will expose its source type and permanent state. Common operations should be consistent where applicable:

- add;
- edit where supported;
- activate or deactivate;
- delete;
- inspect last fetched status;
- select for a manual run.

Source-type-specific fields and validation may remain different.

### 4.2 Permanent active state

Each source has a persistent active/inactive state.

- **Active:** included in the next automated run.
- **Inactive:** excluded from automated runs until reactivated.

Temporarily excluding an active source from a manual run must not make it inactive.

Deactivating a source must not remove its previously collected content or historical digest contributions.

### 4.3 Temporary manual selection

For a manual run, the user can temporarily select the RSS feeds and YouTube channels to process.

This selection applies only to that run:

- it controls which sources are queried for fresh information;
- it does not modify permanent active/inactive state;
- an active but unselected source remains active for the next automated run;
- previously collected content from unselected sources remains in the database and in relevant digests.

By default, active sources should be available as the normal manual-run selection set. The interface may offer select-all, clear-all, and source-type filtering for convenience.

### 4.4 One collective action

A manual run should be initiated through one end-to-end action rather than requiring separate technical steps.

The collective run performs:

1. fetch newly available content from the temporarily selected sources;
2. extract article text or retrieve YouTube transcripts;
3. summarize new or previously unsummarized items;
4. identify every affected publication date;
5. regenerate the complete RSS and/or YouTube digest for each affected date;
6. report results and failures as one run.

The user should not need to understand or trigger scraping, transcript retrieval, item summarization, and digest synthesis independently during normal use.

### 4.5 Separate RSS and YouTube sections

RSS and YouTube remain separate primary sections in the side navigation.

Each section owns its own:

- current daily digest;
- previous/next date navigation;
- historical browsing;
- source footnotes or item list;
- empty states;
- per-date regeneration behavior.

RSS content must appear only in RSS views and RSS digests. YouTube content must appear only in YouTube views and YouTube digests.

### 4.6 Separate histories with feature parity

RSS and YouTube histories remain separate rather than being merged into one mixed history page.

Both should support equivalent behavior:

- browse available dates;
- filter or navigate by year and month where appropriate;
- open a digest for a specific date;
- move to the previous or next available digest;
- clearly indicate dates with no digest;
- preserve access to older content.

Visual presentation may differ where the media type requires it, but date and navigation capabilities should be consistent.

### 4.7 Publication date determines digest date

An item belongs to the daily digest corresponding to its content publication date, not its fetch date and not the date on which the pipeline was run.

Daily date boundaries use IST, consistent with the application scheduler.

Example:

```text
Run executed: June 27 IST
Video published: June 26 IST
Result: video belongs to the June 26 YouTube digest
```

If a single run discovers items published on several dates, every affected date must be processed independently.

## 5. Incremental Processing vs. Complete Daily Digests

The system must distinguish between incremental work and complete digest generation.

### 5.1 Incremental fetching

Only content not already stored should be fetched and inserted.

Existing uniqueness rules should prevent the same RSS article or YouTube video from being added twice.

### 5.2 Incremental item summarization

Only items requiring an individual summary should be sent to the LLM, such as:

- newly fetched items;
- previously failed items explicitly retried;
- items whose summaries are intentionally regenerated.

Previously summarized items should not consume LLM calls again during an ordinary run.

### 5.3 Complete digest regeneration

A daily digest is a synthesis of **all successfully summarized content of that media type published on that date**.

It must not be generated solely from items discovered in the current run.

Example:

```text
June 26 already has 8 summarized RSS articles.
A later run discovers 2 more articles published on June 26.

Individual summarization input: the 2 new articles.
June 26 RSS digest input: all 10 summarized articles.
```

The same rule applies independently to YouTube videos.

### 5.4 Source selection does not restrict digest membership

Temporary source selection controls ingestion for the current manual run. It does not define the final digest corpus.

When an affected digest is regenerated:

- the RSS digest uses all stored, successfully summarized RSS articles published on that date;
- the YouTube digest uses all stored, successfully summarized YouTube videos published on that date;
- previously collected items from sources not selected in the current run remain included;
- previously collected items from currently inactive sources remain included;
- duplicates are excluded;
- items without successful individual summaries remain excluded until processed successfully.

This separation prevents a temporary source choice from accidentally deleting information from an existing digest.

## 6. End-to-End Run Model

### 6.1 Automated run

An automated run should:

1. snapshot all sources whose permanent state is active;
2. fetch fresh content from those sources;
3. process only new or pending items;
4. determine affected publication dates and media types;
5. regenerate complete digests for those affected dates;
6. record a durable run result.

### 6.2 Manual run

A manual run should:

1. display the centralized source list;
2. allow temporary source selection without changing persistent state;
3. start one collective fetch-and-summarize action;
4. process RSS and YouTube branches as required by the selection;
5. regenerate complete digests for every affected publication date;
6. provide links to the resulting RSS and YouTube digests.

### 6.3 Run with only one media type selected

If the user selects only RSS feeds:

- only RSS sources are fetched;
- only affected RSS digests are regenerated;
- existing YouTube digests are not replaced, cleared, or regenerated unnecessarily.

The inverse applies to a YouTube-only run.

### 6.4 Run with no new content

If no new or pending content is found:

- the run completes successfully with a clear “no new content” result;
- no digest is replaced with an empty digest;
- existing digests remain unchanged;
- the source last-checked status may still be updated.

---

## 7. Digest Membership Rules

An item is eligible for a daily digest when all of the following are true:

- it belongs to the relevant media type;
- it has a valid publication timestamp;
- its publication timestamp maps to the digest date in IST;
- it has a successful individual summary;
- it has not been deleted or explicitly excluded from content;
- it is not a duplicate of another stored item.

For YouTube, a description or RSS snippet is not a substitute for a transcript. A video without a usable transcript must not be presented as transcript-derived analysis.

---

## 8. Historical and Late-Arriving Content

Content can be discovered after its publication date because of feed delays, failed extraction, transcript-provider failure, application downtime, or manual backfill.

When late-arriving content becomes successfully summarized:

1. derive its original publication date in IST;
2. mark that media type and date as affected;
3. query all summarized items of that media type published on that date;
4. regenerate the complete historical digest;
5. preserve normal navigation to that updated digest.

Historical digests therefore represent the best complete view of the content currently known to the application, rather than an immutable snapshot of the first run.

---

## 9. Conceptual Information Model

The following concepts should be treated separately even if the current database reuses some tables:

| Concept | Meaning |
|---|---|
| Source | An RSS feed or YouTube channel that can be activated and fetched |
| Source type | The adapter and output section: RSS or YouTube |
| Run | One automated or manual orchestration request |
| Run selection | Temporary snapshot of sources included in that run |
| Item | One RSS article or YouTube video |
| Extracted text | Article body or YouTube transcript |
| Item summary | LLM summary of one item |
| Affected date | Publication date whose complete digest may need regeneration |
| Daily digest | Synthesis of all summarized items of one source type for one publication date |

A run can affect multiple dates and produce multiple digest updates. A digest can be regenerated by multiple runs over time.

## 10. User Experience Expectations

### Central source management

The user should be able to:

- view RSS and YouTube sources together;
- distinguish source types immediately;
- filter the list by source type or status;
- permanently activate or deactivate a source;
- temporarily select sources for a manual run;
- understand that manual selection does not alter permanent state.

### Collective manual run

The interface should communicate one coherent progression, for example:

```text
Queued
  -> Fetching RSS feeds
  -> Discovering YouTube videos
  -> Retrieving transcripts
  -> Summarizing new items
  -> Rebuilding affected RSS digests
  -> Rebuilding affected YouTube digests
  -> Complete
```

Stages that do not apply to the selected source types should be skipped cleanly.

### Result presentation

The completed run should report:

- sources selected and successfully checked;
- new RSS articles found;
- new YouTube videos found;
- transcript successes and failures;
- item-summary successes and failures;
- RSS digest dates created or updated;
- YouTube digest dates created or updated;
- links to each affected digest.

---

## 11. Behavioral Invariants

The future implementation must preserve these rules:

1. Temporary manual selection never changes permanent source state.
2. Automated runs include all and only permanently active sources.
3. A normal manual run is one end-to-end action.
4. RSS and YouTube outputs never merge into one digest.
5. Digest date is based on publication time converted to IST.
6. New items are processed incrementally.
7. Affected daily digests are regenerated from the complete stored corpus for that date and media type.
8. Current run selection never removes previously collected items from a digest.
9. Deactivating a source never rewrites historical content by itself.
10. A no-new-content run never replaces an existing digest with an empty result.
11. Duplicate fetches never create duplicate items or duplicate digest entries.
12. YouTube metadata is never misrepresented as a transcript.
13. A failure in one source or media branch should be visible without hiding successful work from the other branch.

---

## 12. Success Criteria

- [ ] RSS feeds and YouTube channels can be managed from one centralized source interface.
- [ ] Active/inactive state controls automated runs.
- [ ] Manual selection is temporary and does not change source state.
- [ ] One manual action performs fetch, item summarization, and digest generation.
- [ ] RSS output appears only in the RSS section.
- [ ] YouTube output appears only in the YouTube section.
- [ ] RSS and YouTube provide separate but equivalent history and date navigation.
- [ ] Items are assigned to digests by publication date in IST.
- [ ] Late-arriving items cause the relevant historical digest to be rebuilt.
- [ ] Rebuilt digests use all summarized items for the date, not only items from the latest run.
- [ ] Previously summarized items are not unnecessarily summarized again.
- [ ] Manual source selection cannot accidentally make an existing digest incomplete.
- [ ] RSS-only and YouTube-only runs do not disturb the other section.
- [ ] No-new-content runs preserve existing digests.

## 13. Scope Boundary

This document defines the agreed problem statement and product behavior. It does not prescribe the final database migration, API schema, background-job implementation, or UI layout.

The next planning stage should translate these invariants into:

- a run and job data model;
- centralized source-management interactions;
- source-selection request semantics;
- publication-date normalization rules;
- complete digest query rules;
- separate RSS and YouTube history routes;
- failure recovery and status reporting;
- migration and test strategy.

No implementation is authorized by this document alone.
